设备包验收¶

阅读角色

  • 业务负责人：确认可运行范围、审批条件、结果要求和异常处置责任。

  • 开发或运维人员：配置运行模式、资源调度、监控、停止和恢复机制。

  • 验收人员：验证资源冲突、超时、取消、未知结果、安全停机和追溯记录。

本页说明如何验证用户自行准备的设备包。验收目标不是“页面能打开”，而是确认设备、物料、工作流和现场约束在同一个配置版本下能够正确配合。

开始前先用能力检查表确认设备包已经达到“已定义、已加载、已连接、已联调”中的哪一层；验收完成后，按版本与验收记录保存系统版本、设备包版本、启动图（Graph JSON）和结果证据。

先确认验收范围¶

设备包负责人应提供：设备包版本、启动图、运行模式、工作流清单、所需物料、可用设备、风险说明和预期结果。安装人员通过 unilab package inspect 与 unilab workspace status 核对实际加载内容，不能使用记忆中的数量或旧截图判断。

工作流覆盖建议¶

设备包至少应准备以下类型的验收工作流：

  • 只读状态检查：不产生设备动作，用于确认实例和连接；

  • 单动作冒烟测试：用安全参数验证每类设备的一个核心动作；

  • 物料约束测试：验证物料类型、单位、容量、库位和占用规则；

  • 多设备串联测试：验证上一步输出能否正确传给下一台设备；

  • 共享资源测试：两个任务竞争同一设备或库位时应等待，而不是同时占用；

  • 故障测试：设备离线、参数越界、超时和人工取消都要有清楚结果。

创建任务前的业务核对¶

  1. 工作流名称、用途和风险与本次验收一致。

  2. 输入参数标明单位、允许范围和默认值，默认值不会触发危险动作。

  3. 所有设备在线，且实例 ID 与 启动图 一致。

  4. 物料类型正确，数量、容量、状态和当前位置满足要求。

  5. 来源和目标库位存在、空闲且允许放置该物料。

  6. 模拟与真实设备没有混用，生产地址没有进入测试 启动图。

  7. 急停、互锁、人员防护和现场清场已经按管理制度确认。

通用端到端示例¶

下面是一条与具体行业无关的样品处理流程，用于说明验收思路：

  1. 从原料区取得容器并确认容器类型。

  2. 由加料设备按目标量加入物料。

  3. 将容器移动到混合设备，按规定时间和速度处理。

  4. 将样品送到检测设备并记录结果。

  5. 将容器送回指定库位，提交最终物料位置和状态。

验收时为每一步记录：调用的设备实例、输入参数、开始/结束时间、输出、物料位置变化和异常。示例中的设备名称必须替换为用户设备包实际定义的实例，不能照抄为生产配置。

如何判断等待与故障¶

共享设备、机械臂或唯一库位被占用时，任务可以进入等待。应在任务详情中看到具体等待对象；资源释放后任务继续。以下情况应判为故障并处理，而不是无限等待：设备持续离线、目标库位不存在、输入不合法、互锁未满足、动作超过规定超时。

结果验收¶

结果

需要确认

任务成功

所有必要步骤成功，且没有被忽略的设备告警

设备输出

数值有单位和合理范围，文件或检测结果确实存在

物料变化

数量、状态和位置与实际现场一致

调度记录

共享资源没有被重复占用，等待和释放顺序可解释

失败结果

明确指出失败步骤、设备和原因，不把超时当成功

设备发出的“目标值”不一定等于传感器实测值。设备包应为两类字段使用不同名称，并在页面说明其业务含义。

验收完成的判据¶

  • 使用的 Uni-Lab OS、设备包和 启动图 版本均有记录；

  • 关键工作流在规定模式下通过；

  • 参数越界、设备离线和超时能够安全失败；

  • 物料账面位置与现场一致；

  • 生产所需的人工步骤、权限和恢复办法已写入交付记录。

未满足任一项时，应记录问题并回到相应的设备、物料或部署章节修正。
